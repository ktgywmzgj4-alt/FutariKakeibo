## 1. 結論（先に）

1. **アプリの中身は公開に近い。** CI は 352件全件成功。今朝 2.0.0 (2026.1022.404) が内部テスターに配られた。外部への通信は無く、ログは配信するビルドに出ない
2. **公開を止めているのは、おもに「公開のための外側」。** プライバシーポリシーの公開URL・運営者名・問い合わせ先が無い（アプリの中のリンクも無く、開発用のメモが画面に出ている）。Privacy Manifest の理由つきAPIの申告が空。掲載文案に実装と違う言い方（「ふたりだけ」「画像は外に出さない」）。App Store Connect の入力（サポートURL・年齢区分・審査メモ・スクリーンショット）
3. **共有は「共有のURLを知っている人なら参加できる」形のまま。** Security Roles が初期どおりでも「招待した2人だけが使える」とは言えない。合言葉は1回・1日、参加者は画面で見え、作った人は全員を外せる。ただし、URLそのものが漏れると、共有をやめて始め直しても同じURLで入れる。**初回公開をこの形で出すか、名指しの形に移してから出すか**を決めてほしい（推奨は「この形で、説明を正確にして出す」。9章 D1）
4. **実機で確かめていないことが多い。** 取り戻し・オフライン・同時編集・削除が戻らないこと・入り直し・閉じているあいだの通知・AIが動く端末での読み取り。**本番の家計簿を消さずに試すには、テスト用の2台と2つの Apple ID が要る**（9章 D8、付録A）
5. 初期ユーザーの特典は、公開前にコードの準備は要らない見込み（Apple の AppTransaction で後から判定できる）。ただし掲載文で約束しすぎないこと（6章）

## 3. 共有とデータ保全（優先順位1）

前提の監査は `Docs/SHARING_SECURITY_AUDIT.md`（T-040・T-041）、移す計画は `Docs/SHARING_MIGRATION_PLAN.md`（T-048）。ここでは公開の判断に要る形にまとめ直し、コードで確かめた。

### 3-1. 第三者が参加できる条件

- `CloudKitSyncService.sharePublicPermission = .readWrite`（`CloudKitSyncService.swift` 1198行）。共有（CKShare）は**共有のURLを知っている人なら誰でも参加でき、読み書きできる**
- 参加の入口は2つ: (a) 合言葉（8文字。0・O・1・I・L を除く31文字から、暗号用の乱数で。24時間）→ 公開データベースの `invite-<合言葉>` から共有のURLを引く。(b) 共有のURLそのもの
- 参加できる人: 使われる前の合言葉を期限内に知った人（先着1人）／**共有のURLを知っている人（期限なし。共有が続くかぎり）**／作った人・参加した人の Apple ID に入れる人
- Security Roles（初期どおり）が守るのは、公開データベースにある合言葉のレコード（他人が書き換え・消せない）。**家計のデータに誰が入れるかは CKShare の公開の権限で決まる**ので、Security Roles だけでは「2人だけ」と言えない
- 公開データベースは、このアプリ（署名したもの）か、開発者が作る API トークンからしか読めない（トークンは無い、利用者が確認）。合言葉のレコードは名前を知らないと読めない（`ShareInvite` に Queryable の索引は無い、利用者が確認）

約束の言い方の案（requirements.md・safety.md は利用者が直す）:
「家計のデータは、家計簿を作った人の iCloud の中の、共有に参加した人だけが読める場所に置く。参加は、合言葉か共有のリンクを知っている人ならできるので、合言葉は相手にだけ伝える」

### 3-2. 合言葉の1回利用と期限（コードで確かめた）

| 守り | 仕組み | 自動テスト | 限界 |
| --- | --- | --- | --- |
| 1回だけ | 参加する前に `invite-used-<合言葉>` を作る。同じ名前は1つしか作れないので先着1人（`claimInvite`） | `SharingSafetyTests` | 共有のURLを直接読めば、アプリの確認を通らない |
| 期限 | 24時間（`ShareInvite.lifetime`）。アプリが比べる（`resolveInvite`） | 同上 | 端末の時計をずらすと通せる（1回の印は効く） |
| 後片付け | 使われた・期限切れの合言葉を、発行した端末が消す（`tidyIssuedInvites`） | 同上 | この版より前に発行した合言葉は、控えが無いので消せない（期限は切れている） |

### 3-3. 共有のURLが漏れたときの取消

- **いまできること:** 作った人の「共有をやめる（全員が外れます）」。その時点で全員が入れなくなる。家計のデータは消えない
- **できないこと:** 1人だけ外す。URLを変える（同じ家計簿を共有し直すとURLは同じ。Apple の `CKShare.url` の説明）。つまり、**漏れたURLは、共有を始め直すとまた使える**
- 根本の直しは「参加者を名指しする共有」（T-048。3-5）

### 3-4. 参加者の確認

- 共有の画面に参加している人（名前は iCloud が教えてくれるときだけ）と人数。ふたりより多ければ赤字で知らせる（`strangerCount`）
- 参加する前に、作った人が承認する仕組みは無い（名指しの共有か、iOS 26 の「参加の申し込み」が要る）

### 3-5. 既存の利用者を安全に移す方法（T-048 の再利用）

- 推奨は**案A: 同じ置き場所のまま、公開の権限を外して名指しにする**。データは動かさない。いまの相手は一度外れ、名指しの招待を受け直す。うまくいかなければ公開の権限を戻せば、前と同じURLで入れる
- 移す前の条件: `ShareMigrationReadiness`（作った人の端末であること・5分以内に同期済み・送信待ちのレシート画像が無い）。CI確認済み、画面からはまだ使わない
- 確かめが要ること: ユーザーレコードIDで名指しできるか（Apple の資料はメール・電話の例だけ）、iOS 17・18 の端末での動き。Development の環境で確かめる（`ios-dev-build.yml` はプロファイルを作り直すので、動かす前に承認が要る）
- 案C（公開後の新しい利用者だけ、最初から名指し）は既存の共有に触れずに済むが、作る量と確かめる量は案Aと変わらない

### 3-6. 未同期データの保護と、移行に失敗したときの復旧

- 同じ家計簿に入り直すときは置き換えずに突き合わせ、手元にしか無い記録・削除印・送信待ちのレシート画像・新しい設定を残す（`AppStore.snapshotAfterJoining`・`isSameHousehold`。`RejoinSnapshotTests`・`SharingMigrationPreparationTests`）。CI確認済み、実機は未
- 移行に失敗したら、公開の権限を戻す（同じURL）。家計のデータは作った人の iCloud に残る

## 4. 無料のレシート読み取り（優先順位2）

### 4-1. いまの作り（コードで確かめた）

- **文字の読み取り:** Vision（`VNRecognizeTextRequest`、revision 3、accurate、ja-JP・en-US、言語の補正あり）。端末の中だけ
- **解析:** ルール（`ReceiptParser`。候補と点数、足し算での照合、店と品の辞書、覚えた店）。ここまではすべての端末で動く
- **AI補助:** `ReceiptInterpreter` が、iOS 26 以降で `SystemLanguageModel.default.availability` が available の端末だけ、同じ文字を端末内のモデルに読ませ、答えの取れた項目だけ差し替える。
  根拠のある値（合計の語・辞書の店名・品の値段の重さで決めた種類）は上書きしない。足し算と食い違う合計、ありえない日付は捨てる
- **AIが使えない端末・答えが無いとき:** ルールの結果のまま（`OnDeviceReceiptReader.read` が nil）。利用者の iPhone 13・SE2 はこちら
- **合計と日付:** 合計に根拠が無い・足し算と合わないときは「合計金額をレシートと見比べてください」。日付が読めないときは入力を促す。3年より前・明日より後の日付は捨てる（AIの答えは10年より前・明日より後）。**範囲の中での読み違いには目印が無い**（保存前に画面で確かめてもらう）
- **通信:** 無い（`URLSession` も http も無い）
- **ログ:** `print` を出す処理はすべて `#if DEBUG` の中。配信するビルドには出ない

### 5-2. 「データを集めていない」と言えるか（Apple の定義と照合）

Apple の定義（App privacy details）: 「"Collect" refers to transmitting data off the device in a way that allows you and/or your third-party partners to access it for a period longer than what is necessary to service the transmitted request in real time.」
「Data that is processed only on device is not "collected"」。CloudKit は Apple のサービスの例に挙がり、「You are not responsible for disclosing data collected by Apple.」。
**iCloud の中で開発者が読めないデータについて、明記した文は無い。**

| データ | 置き場所 | 開発者が読めるか | 定義に照らして |
| --- | --- | --- | --- |
| 支出・収入・名前・予算・覚えた店・レシート画像 | 作った人の iCloud の Private Database（共有なら参加者も） | 読めない | 「あなたがアクセスできる」に当たらない、と読める（明記は無い） |
| 合言葉のレコード（共有のURL・期限）と、使われた印（期限） | CloudKit の公開データベース | **読める**（CloudKit Console。レコードの名前を知っていれば）。作った人の利用者ID（CloudKit が付ける）が付く。後片付けの前や、この版より前の合言葉・使われた印は1日より長く残る | **User ID の収集に当たりうる** |
| 端末の通知の登録 | Apple（CloudKit が送る） | 受け取らない | 当たらない |
| レシートの文字 | 端末の中だけ | — | 当たらない |

→ **「iCloud だけだから収集なし」とは言えない**（公開データベースがある）。申告の方針は 9章 D2。

## 6. 初期ユーザーの無料特典（判断材料。いまは何も作らない）

### 6-1. 見分け方: Apple の AppTransaction

- `AppTransaction` は「Information that represents the customer's purchase of the app, cryptographically signed by the App Store.」。iOS 16 から使える（このアプリは iOS 17 から）
- `originalPurchaseDate`: 最初に入手した日。`originalAppVersion`: 最初に入手した版。**iOS では版の文字列ではなくビルド番号（CFBundleVersion）**で、更新しても変わらない
- Apple の例は「有料アプリを無料＋アプリ内課金に変えたとき、前に買った人に機能を残す」。比べる値はビルド番号
- テスト環境（サンドボックス）では `originalAppVersion` は常に「1.0」。**TestFlight では本当の値を確かめられない**
- 無料アプリでも使えるか、再インストール・機種変更で同じ値になるかは、Apple の資料に明記が無い。入手の記録は Apple Account に結びつくので、**同じ Apple Account なら同じ値になる見込み（未確認）**

### 6-2. 決めてほしいことと材料

| 決めること | 案 | 材料 |
| --- | --- | --- |
| 対象 | (a) 締切の日までに初めて入手した Apple Account（`originalPurchaseDate`）／(b) 基準のビルドより前に入手（`originalAppVersion`）／(c) 家計簿ごと（どちらかが対象なら2人とも）／(d) 先着N人 | (a) がいちばん分かりやすい。(b) はビルド番号が「2026.1022.404」の形なので、文字のまま比べると誤る（数として比べる）。(c) は共有の記録に印を足すことになり、そのとき CloudKit Production のスキーマ追加（承認）が要る。(d) は端末から数えられず、サーバーが要る |
| 期間 | 期限なし／有料化から一定期間／回数の上限を上げる形 | 「永久」と書くと後で変えられない。決めるまでは掲載に期間を書かない |
| 有料化しても特典を残せるか | 残せる | 判定は Apple の署名つきの記録を端末で読むだけ。サーバーも独自アカウントも要らない。有料の機能はアプリ内課金で開ける（審査 3.1.1） |
| 再インストール・機種変更 | 同じ Apple Account なら残る見込み | Apple Account を変えた人は対象から外れる |
| 回数の上限 | 決めるのは有料化のとき | 端末の中で数える（消せば戻る）／iCloud に残す（スキーマ追加）／サーバー（費用・プライバシー） |

### 6-3. 公開前に最低限要ること

- **コードは要らない見込み**（後から AppTransaction で判定できる）
- 掲載文で約束しすぎない: 「いまは全部の機能が無料」まで。対象・期間を決めるまで「ずっと」「永久」と書かない。スクリーンショット・サブタイトルに価格や条件を入れない（2.3.7）
- 締切を日付で決めるなら、公開した日と、公開したビルド番号を記録しておく（この文書と progress.md に残す）
- 後から対応した場合の制約: 判定は Apple Account ごと。家計簿ごとに優遇するなら、そのときに共有の記録へ印を足す（スキーマ追加）。実機での本当の値の確認は App Store 版でしかできない

## 付録B 審査メモの原稿（App Store Connect の「Notes for Review」）

```
Futari Kakeibo is a household budget app for two people. No sign-in or account is needed.
Data is saved on the device. When the user starts sharing, it is stored in the user's iCloud (CloudKit).
We operate no servers and do not receive user data.

How to review sharing (two iPhones signed in to different Apple Accounts with iCloud are needed):
1. iPhone A: 設定 tab > 共有をはじめる > 合言葉を発行する. An 8-character code appears.
2. iPhone B: 設定 tab > 共有をはじめる > enter the code > この合言葉で参加する.
3. Add an expense on either iPhone (追加 tab). It appears on the other within about 30 seconds.
With a single iPhone, you can still issue a code and see the sharing screen.

Receipt scanning: 追加 tab > レシート > カメラで撮る. Text recognition runs on the device (Vision).
On devices with Apple Intelligence, the on-device model may help fill in fields. Nothing is sent off the device.

Notifications about the other person's new expenses are off by default (設定 tab > 通知).
They are created on the device after a silent CloudKit signal; they do not include amounts or store names.
```
